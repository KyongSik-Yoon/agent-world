# 화면 성능

화면 회귀는 거의 다 두 가지다.

1. **장면 프레임 밖에서 화면이 나간다.** CSS transition·애니메이션, 따로 도는 rAF 처럼 장면이 쉬는 박자에 한 장씩 더 내보내는 것이다. 크롬이 화면 한 장을 내보내는 데는 무엇이 바뀌었든 고정비가 든다(4K 60Hz 에서 장당 약 14ms, 그중 4ms 는 바닥값). 그래서 장 수가 곧 CPU 다.
2. **조용해야 할 때 장면 박자가 오른다.** 장면 밖 입력, 끝나지 않는 비행·전환 같은 것들이다.

장면은 평소 30장, 조작 중 60장(120Hz 화면에서도 60), 곁눈질 3장으로 그린다(`web/world/scene.ts` 의 `pace`). 곁눈질로 내려가는 데는 20초, 손가락으로 쓰는 기기(`pointer: coarse`)는 5초다 — 프레임 검사는 마우스 화면이라 20초 쪽만 본다. 박자 있는 움직임은 `web/beat.ts` 로, 이름표의 움직임은 `web/world/labels.ts` 로 장면 프레임에 얹는다.

## 돌리기

```sh
bun run perf:lint            # 몇 초. 끝없는 CSS 애니메이션, 이름표 층의 transition, 장면 밖 rAF, 짧은 setInterval, backdrop-filter
bun run perf                 # 2분 남짓. 불변식을 보고, 통과하면 커밋된 web/ 트리의 통과 기록을 남긴다
bun run perf --compare       # origin/main 과 번갈아 3회 재서 비용을 비교한다(경고만, 막지 않는다)
bun run perf --compare <ref> --rounds 5
bun run perf --only 끌기,고르기   # 그 시나리오만(기록은 남기지 않는다)
```

- **push 와의 관계:** main 으로 가는 push 는 `.githooks/pre-push` 가 린트를 돌린다. web/ 이 바뀐 묶음이면 그 web/ 트리의 통과 기록도 요구한다. 그러니 커밋한 뒤에 `bun run perf` 를 돌린다. web/ 에 커밋하지 않은 변경이 있으면 기록이 남지 않는다.
- **예외 표식:** 의도한 예외는 그 줄이나 윗줄에 `perf-ok: <이유>` 를 단다. 여러 줄이면 `perf-ok-block:` … `perf-ok-end` 로 감싼다. 이유에는 "왜 쉬지 않고 돌지 않는가"를 쓴다. "필요해서"는 이유가 아니다.

## 시나리오와 불변식

| 시나리오 | 무엇 | 장면/s | 출력 |
|---|---|---|---|
| 평소 | 초점 있음, 입력 없음 | 26~34 | ≤ 장면×1.1+1 |
| 장면 밖 입력 | 위쪽 막대 위 포인터, 검색창 키 | 26~34 | 〃 |
| 끌기 | 장면을 끌어 돌림 | 48~62 | 〃 |
| 고르기 | 작업 중 주민을 골라 가운데 터미널이 흐름 | 26~34 | 〃 |
| 곁눈질 | 20초 넘게 무입력, 터미널은 계속 흐름 | 2~4.5 | 〃 |
| 끌기·박자 거르기 | `?perf-skip=1` — 120Hz 화면을 흉내 내 한 박자씩 거름 | 20~34 | 〃 |

- "장면 밖 입력"에 목록 줄 위 올려놓기와 검색으로 걸러 보기는 넣지 않았다. 둘은 캐릭터가 반응하는 0.8초 동안 일부러 주사율 그대로 그린다(`ease()`).
- 시나리오는 `dev/perf/scenario.json`(`dev/perf/gen-scenario.ts` 로 만든다)이고, 가상 herdr(`dev/mock-herdr.ts`)에 물린다.
- 한 번 잰 값이 어긋나면 한 번 더 재서, 두 번 다 어긋나야 실패로 친다.
- 표의 main ms/장·스타일/장·렌더러%·GPU% 는 비용 참고치다. 막지 않는다.

## 실패했을 때

**출력 > 장면** — 장면 밖에서 무엇이 화면을 내보낸다.

- 먼저 `bun run perf:lint` 를 본다. 대부분 여기서 잡힌다.
- 안 잡히면 추적으로 찾는다. 시나리오를 재현한 페이지에서 CDP `Tracing` 을 `viz,devtools.timeline` 로 걸고, `Display::DrawAndSwap` 마다 직전 60ms 의 `CrRendererMain` 이벤트를 본다. 스크립트 없이 스타일 계산만 있는 출력이면 transition·애니메이션이다.
- 어느 요소인지는 `disabled-by-default-devtools.timeline.invalidationTracking` 의 `StyleRecalcInvalidationTracking` 에서 이유가 `Animation` 인 노드로 찾는다. 2026-11-20 의 이름표 transition 이 이렇게 나왔다.

**장면 박자가 범위 밖** — `pace()` 를 붙드는 것을 찾는다. `lastInputAt`(장면 밖 입력이 `aimedAtScene` 을 통과하지 않는지), `easeUntil`, 끝나지 않는 `flight`, 걷는 캐릭터의 그림자 같은 것들이다.

**오류(무대가 안 열림, 캔버스가 아님 등)** — 화면 구조가 바뀌어 시나리오가 못 따라간 것이다. 시나리오를 고친다. 검사를 끄지 않는다.

## 비용을 비교할 때의 함정

- **헤드리스 한 번 잰 값은 ±30% 흔들린다.** `--compare` 로 번갈아 여러 회 재서 가운데 값만 믿는다. 부하 평균이 높으면(다른 세션의 시험) 결과가 2배까지 흔들린다. `/proc/loadavg` 를 같이 본다.
- **JS 프로파일러(100µs 표본)는 끄는 동안 three.js 가 두 배 느린 것처럼 보이게 했다.** 껐더니 같았다. 장당 시간은 `Performance.getMetrics` 의 `TaskDuration` 이나 rAF 콜백 시간으로 재고, 프로파일은 어디인지 찾을 때만 쓴다.
- **헤드리스는 60Hz 다.** "장면 < 화면 박자"일 때만 드러나는 회귀는 `?perf-skip=1` 로 드러낸다. 배율 2·큰 창에서는 GPU 가 화면을 읽어 오는 비용(SwapBuffers)으로 포화돼 차이가 묻힌다. 배율 1·1600×1000 으로 잰다.
- **끌기를 시작한 자리가 캔버스인지 확인한다**(`elementFromPoint`). 이름표 위를 누르면 카메라가 안 돌아 "회귀"로 잘못 읽는다.
- 프로세스를 끌 때 `pkill -f <문자열>` 을 쓰지 않는다. 그 문자열을 담은 내 셸도 죽는다. 포트로 pid 를 찾아 끈다.
- **CDP 포트가 겹치면 남의 크롬에 붙는다.** 띄운 뒤 그 포트를 쥔 pid 가 내 프로필인지 확인한다(`run.ts` 가 한다).

## 휴대폰 크기에서 재기

- 390×844·배율 3·터치 흉내(`pointer: coarse` 가 맞는다)의 GPU 헤드리스로 잰다. 실제 세션은 보기 전용 서버(`AGENT_WORLD_READONLY=1`, 임시 `XDG_STATE_HOME`)에 붙여
  최근에 움직인 주민을 골라 보고, 고친 판은 같은 실제 세션에 서버를 하나 더 띄워 앞 판과 번갈아 잰다. 보기 전용 서버는 `control` 이 없어 입력창이 숨고
  크게 보기의 휠 신호도 안 나간다 — 글 치기·넘기기 왕복은 가상 herdr 로 잰다.
- **GPU 가 하는 일은 CPU 로 다 안 잡힌다.** 내장 GPU 의 `/sys/class/drm/card1/device/gpu_busy_percent` 를 100ms 마다 읽어 함께 본다(데스크톱 전체 값이라
  번갈아 재서 차이만 믿는다). 휴대폰 상태 창 밑의 유리 흐림은 GPU 프로세스 CPU 로는 −20% 였지만 GPU 바쁨으로는 절반이었다.
- **화면을 다 덮는 불투명한 창과 그 밑에 깔린 것에 `.glass` 흐림을 남기지 않는다.** 보이지 않아도 GPU 가 장마다 그 밑을 다시 흐린다.
- 앞 페이지의 렌더러가 재는 동안 끝나면 렌더러 CPU 합이 음수로 나온다. 시작과 끝에 다 있던 pid 만 더한다.
- 재 보니 비용이 아니었던 것: 접은 줄의 `position: sticky`(끄면 크게 보기 넘기기가 오히려 늘었다), 크게 보기 입력칸의 커서(`caret-color: transparent` 로도
  초당 2장 그대로, 합 2%), 크게 보기 넘기기가 장마다 칠하는 것(`will-change`·`contain: paint` 로도 같다 — 손가락으로 넘기는 동안만 든다).

## 실제 창에서 재기(수동)

절대 수치(사용자 화면에서 몇 %)가 필요할 때만 한다. 헤드리스는 화면 박자·화소 수·GPU 부하가 실제와 달라, 비교는 되지만 절대 수치는 맞지 않는다.

1. **사용자의 모니터를 빌리기 전에 묻는다. 승인은 매번 받는다.** 앱 창이 떠 있는 모니터의 주사율부터 확인한다. 120Hz 같은 빠른 화면에서만 드러나는 것이 있다.
2. 같은 크롬을 따로 띄운다. 임시 `--user-data-dir`, 알아볼 창 클래스, 드문 디버깅 포트를 쓴다. 그 창이 그 모니터에 보이게 둔다(가려진 창은 rAF 가 멈춘다).
3. 앞 판과 새 판 서버를 같은 가상 herdr 에 붙여 번갈아 3회 잰다. CPU 는 `/proc` 의 프로세스·스레드별 시간으로, 화면 출력은 `Display::DrawAndSwap` 으로 잰다.
4. 끝나면 사용자의 화면을 원래대로 돌리고, 띄운 것을 pid 로 끈다.

함정:

- 이렇게 띄운 크롬의 루트 프로세스는 명령줄이 인자 하나로 뭉쳐 있을 수 있다. `\0` 구분을 가정하고 찾지 않는다.
- CDP 로 보낸 입력도 `isTrusted` 라서 실제 입력과 구별할 수 없다. 측정 동안 실제 포인터가 그 모니터 위에서 움직였는지는 따로 본다.
- 모니터가 꺼져 있으면(잠금) 곁눈질은 0장이다.
